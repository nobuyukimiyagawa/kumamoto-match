# 設計メモ（実装の前提）

熊本県内のアマチュアサッカー向けマッチングサービス。
**FC VALIANT のサイトとは別のアプリケーション**として作る。

仮称: **ピッチメイト**（正式名は未定。`src/config/site.ts` の1か所で変更できるようにする）

## 決定事項

| 項目 | 決定 | 理由 |
|---|---|---|
| 現行サイトとの関係 | 完全に分離 | 対戦相手のクラブが運営する場所には、他チームは募集を出しにくい |
| 対象範囲 | 熊本県内のみ | 会場候補が有限で、距離計算も単純な平面近似で足りる |
| 地図 | MapLibre + OpenFreeMap | 鍵も費用も不要。地名は name:ja を優先 |
| 機能 | チーム間・チーム対個人の両方 | 募集と応募という骨格が共通なので同時に作れる |

## 2種類の募集

骨格は同じ。`kind` で分岐させ、テーブルは分けない。

- `training_match` … チーム間のトレーニングマッチ。募集主=チーム、応募者=チーム
- `helper` … 試合の助っ人。募集主=チーム、応募者=個人

## アカウントは1種類、画面は「チーム」と「個人」で分ける（2026-09-15 改定）

データ上のアカウントは1種類のまま（個人が後からチームを作る／チームの人が助っ人にもなる動きを壊さないため）。
**入口と管理画面は分ける**:

- 新規登録 `/signup/` → 「チームとして登録」`/signup/team/`／「個人として登録」`/signup/player/`。
  選んだ種類は localStorage（`pitchmate-signup-role`）に控え、認証から戻った `/welcome/` が手順を変える
  - 個人: プロフィール → 完了（募集を探す）
  - チーム: 代表者のプロフィール → チーム登録 → 完了（募集を出す）
  - 種類が分からない（別ブラウザでメール確認した等）ときは `/welcome/` で先に選んでもらう
- 管理画面: `/me/`＝個人（助っ人エントリー・個人としての評価）、`/team/`＝チーム管理（募集と承認・対戦エントリー・チームとしての評価）。
  両方使う人は相互リンクで行き来する。ログイン後の行き先はチームを運営していれば `/team/`、そうでなければ `/me/`
- 共通部品は `src/components/ManagePanels.tsx`、チームの作成・編集フォームは `TeamForm.tsx`

課金の対象はチームなので、チーム側にだけ「オーナー」「請求先」を持たせる。

## データ構造

```
profiles         個人。auth.users と 1:1。表示名／ポジション／経験年数
                 ※ 住所は持たない。活動エリアは郵便番号から引いた「市区町村＋町名」まで
                   （例: 熊本市中央区水前寺）。郵便番号と番地は保存しない（2026-09-14 決定）
teams            チーム。名前／紹介／ホーム会場／レベル帯／オーナー
team_members     チームと個人の多対多。role = owner | admin | member
venues           会場。名前／住所／緯度経度。地図に出すのはここだけ
posts            募集。kind / team_id / venue_id / 日時 / 想定レベル / 人数 / 本文 / status
applications     エントリー。post_id / エントリー者（team_id または profile_id）/ status / メッセージ
                 status: pending（承認待ち）→ approved（エントリー完了）| rejected（見送り）| cancelled
ratings          五つ星評価。application ごとに 募集主チーム⇔エントリー者 の両方向、各1回
                 試合日を過ぎた approved の相手にだけ付けられる
```

### エントリーの流れ

1. 探す → 募集詳細 → 「エントリーを送る」（助っ人=個人、トレーニングマッチ=チームの運営者）
2. 募集主のマイページ「チームの管理」に承認待ちが並ぶ。相手の評価（平均・件数・最近のコメント）を見て「承認」か「見送り」
3. 承認で **エントリー完了**。助っ人は定員に達したら募集が「成立」、トレーニングマッチは1チーム承認で「成立」
4. 試合日を過ぎたら、マイページ「評価する」に相手が並ぶ。星1〜5と一言。相手の一覧・詳細に表示される

### 位置情報の扱い（厳守）

**地図に出してよいのは `venues` だけ。個人・チームの所在地は地図に出さない。**
「近く」の基準は、利用者がその場で選んだ現在地または市区町村から計算する。
個人の居場所が地図に出るサービスは使われない。

`profiles` に緯度経度のカラムを作らないことで、構造的に守る。

## 画面

### 探す `/`
- スマホは上=地図・下=縦リスト、PCは左=リスト・右=地図。ピンとカードは双方向に連動
- 絞り込み: 日付、種別、場所（会場の市区町村）、現在地から◯km以内、レベル
  - 日付は **既定で「今日」**。チップ「今日／明日／カレンダー／すべての日程」。カレンダーは月表示で
    **日ごとの募集数** を出す（`Calendar.tsx`）。件数は日付以外の条件を適用したあとで数える
  - 選んだ日に募集が無ければ「次に募集があるのは◯月◯日（n件）」と案内し、その日へ飛べる
  - 場所チップの件数は日付に関係なく数える（場所→日付の順でも探せるように）
- カードに募集主チームの評価とエントリー数

### 募集する `/post/new`
- チームの運営者だけ。種別 → チーム → 日時 → 会場 → 条件 → 本文

### 募集の詳細 `/post/?id=`（静的書き出しのためクエリで受ける）
- 条件、会場地図（Google マップへのリンク付き）、募集主チームの評価と最近のコメント
- エントリー者には「エントリーを送る」／自分のエントリー状況
- 募集主には「エントリー一覧」＋承認／見送り（相手の評価・プロフィール・メッセージ付き）

### マイページ（個人） `/me`
- 自分のプロフィールと助っ人としての評価、チーム管理への入口
- タブ「助っ人エントリー」／「評価する」（個人として未評価の相手）。未処理件数をバッジで出す

### チーム管理 `/team`
- 運営チームの概要（複数ならチップで切替）、編集・別チーム作成・募集するボタン
- タブ「募集とエントリー」（出している募集と承認、対戦エントリー、終わった募集）／「評価する」（チームとして未評価の相手）

### チームを作る `/team/new`
- 作った人がオーナー。個人が後からチームを持つ動線

## データ層（いま）

Supabase 未接続。`src/lib/store.ts` が localStorage で同じ構造を持ち、全フローが動く。
ログインの代わりにヘッダーの「アカウント」でデモ用プロフィールを切り替える。
Supabase に移すときは store.ts の関数の中身だけ差し替える（画面は store の関数しか呼ばない）

## 見た目（2026-09-15 改定: RADAR UI）

黒地に白文字、信号色は「レーダーの緑」ひとつ。SF のレーダー探査画面をモチーフにする。
**ただし読みやすさと押しやすさは落とさない**（以前「黒地は見にくい」と指摘があったため、
本文は #eef2f6、補助文字は #a9b3bf でカード地に対して 8:1 を確保している）。

- トークンは `src/app/globals.css` の `:root` に集約。部品はすべて `@layer components`
- 書体: 和文＝BIZ UDPGothic（変更なし）／英数字の見出し＝Orbitron（ロゴ）／計器の数値＝Share Tech Mono
- 地図: OpenFreeMap の `dark` スタイル。上に掃引（conic-gradient を回転）・同心円・十字線・四隅の枠を
  `pointer-events: none` で重ねる。掃引の中心は現在地があればそこ、無ければ画面中心（`SearchMap.tsx` の placeRadar）
- 地図左上の計器（件数・種別内訳・中心座標・ズーム）は PC のみ表示
- ピン＝反応点。種別色の丸＋文字。選択中は緑で塗る
- カードは四隅に短い括弧。選択中は緑の枠と発光
- 画面全体に薄いグリッドと走査線。`prefers-reduced-motion` では掃引を止める
- 種別の色はそのまま（トレマ＝シアン、助っ人＝アンバー）。Google／LINE のボタンは各社の色を維持
