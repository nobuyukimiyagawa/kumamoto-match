# 設計メモ（実装の前提）

熊本県内のアマチュアサッカー向けマッチングサービス。
**FC VALIANT のサイトとは別のアプリケーション**として作る。

仮称: **ピッチメイト**（正式名は未定。`src/config/site.ts` の1か所で変更できるようにする）

## 決定事項

| 項目 | 決定 | 理由 |
|---|---|---|
| 現行サイトとの関係 | 完全に分離 | 対戦相手のクラブが運営する場所には、他チームは募集を出しにくい |
| 対象範囲 | 熊本県内のみ | 会場候補が有限で、距離計算も単純な平面近似で足りる |
| 地図 | Google Maps | 利用者に馴染みがある。従量課金は要監視 |
| 機能 | チーム間・チーム対個人の両方 | 募集と応募という骨格が共通なので同時に作れる |

## 2種類の募集

骨格は同じ。`kind` で分岐させ、テーブルは分けない。

- `training_match` … チーム間のトレーニングマッチ。募集主=チーム、応募者=チーム
- `helper` … 試合の助っ人。募集主=チーム、応募者=個人

## 管理画面は1つ

アカウントは1種類。所属の有無で表示を出し分ける。分けると二重保守になり、
個人が後からチームを作る／チームの人が個人として助っ人登録する動きで破綻する。

課金の対象はチームなので、チーム側にだけ「オーナー」「請求先」を持たせる。

## データ構造

```
profiles         個人。auth.users と 1:1。表示名／ポジション／経験年数／活動できる曜日
                 ※ 住所は持たない。活動拠点は「市区町村」までに丸める
teams            チーム。名前／紹介／ホーム会場／レベル帯／オーナー
team_members     チームと個人の多対多。role = owner | admin | member
venues           会場。名前／住所／緯度経度。地図に出すのはここだけ
posts            募集。kind / team_id / venue_id / 日時 / 想定レベル / 人数 / 本文 / status
applications     応募。post_id / 応募者（team_id または profile_id）/ status / メッセージ
```

### 位置情報の扱い（厳守）

**地図に出してよいのは `venues` だけ。個人・チームの所在地は地図に出さない。**
「近く」の基準は、利用者がその場で選んだ現在地または市区町村から計算する。
個人の居場所が地図に出るサービスは使われない。

`profiles` に緯度経度のカラムを作らないことで、構造的に守る。

## 画面

### 探す `/`（既定は地図）
- 上半分に Google Maps。ピンは会場。既定の絞り込みは「今週・熊本県内」
- 下半分に横スライドのカード。地図と双方向に連動する
  （ピンを押す → カードが移動 ／ カードを送る → ピンが強調）
- 絞り込み: 日付、種別（トレーニングマッチ／助っ人）、レベル、募集中のみ
- 地図なしでも使えるよう、一覧表示に切り替えられること

### 募集する `/post/new`
- 種別を選ぶ → 日時 → 会場 → 条件 → 本文
- 会場は登録済みから選ぶか、地図から新規に置く

### 募集の詳細 `/posts/[id]`
- 会場地図、条件、応募ボタン。ログイン前でも読める（検索流入のため）

### マイページ `/me`
- 自分の募集と応募の一覧。チームに属していればチームの募集も

## 段階

1. **今回**: データ構造、探す画面（地図＋カード連動）、募集フォーム。データは仮
2. 次: Supabase 接続、ログイン、応募の実処理
3. その後: 通知、チーム管理、課金

## 外部サービス（利用者の用意が必要）

- Google Maps JavaScript API のキー（請求先の設定が必要）
- Supabase のプロジェクト（認証とデータベース）

どちらも未設定でも画面が壊れないようにする。地図キーが無い場合は
同じ内容を一覧で出す代替表示に落とす。
